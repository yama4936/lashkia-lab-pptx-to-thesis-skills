# 卒業発表のどの部分を、卒論でどう書くか

2026年11月27日にCiiiiNiiiiiiiiの論文一覧21件と添付32ファイルを確認した。卒論20本（PDF計522ページ）の章構成を調べ、うち発表資料がある10組（PPTX 8組、発表PDF 2組）で同じ研究の記述を照合した。別途収録された学会論文と発表資料の1組は、卒論の書式集計から除いた。以下は収録例から得た執筆上の手掛かりであり、学科の提出要領は年度ごとに確認する。

## 章立てを決める

開発を中心とする収録例が多い。20本中19本は第2章で開発環境・使用技術を扱い、その後の本論で自作したものを説明している。残る1本は関連研究と提案システムを先に示し、開発環境と評価を後に置く。背景や既存製品との比較を序論で済ませる例もある。目次は読者が理解するための順序で組む。

- **アプリ・システムの開発**では「序論 → 使用技術と選定理由 → 全体構成と主要機能 → 動作確認・限界 → 結論」を出発点にする。構成図を示した後、機能ごとに利用者の操作、内部の処理、画面や保存内容の変化を結び付ける。
- **手法やモデルの比較**が貢献なら、データ、比較条件、指標を先に定義してから結果と解釈を書く。比較が本論の一部に収まる例も、独立した実験章を置く例もある。同一条件で比較できた範囲を明示する。
- **利用者による評価**がある場合は、何を確かめるために、誰に、何をしてもらい、どのように集計したかを結果より先に書く。自由記述や試用時の観察も、それぞれの取得方法を添える。試作品のデモだけでユーザーへの効果を結論づけない。

## スライドから本文への対応

| 発表に出てくるもの | 卒論で展開する内容 | 手元の資料にない場合の質問例 |
| --- | --- | --- |
| 背景・既存のもの・目的 | 序論で、利用者がどんな場面で何に困るか、既存手段でどこまでできるかを示し、今回確かめる問いや実現したい機能につなぐ。 | 「既存手段で解決できなかった場面を一つ教えてください。」 |
| 構成図を数枚かけて表示する発表 | 全体図を一つ選び、データがどこから来て、どこで変換・保存され、何が返るかを本文で追う。開発環境には各技術の担当と、再現に必要なバージョンを書く。 | 「この矢印で渡すデータは何ですか。どの部分を自作しましたか。」 |
| 機能一覧・画面・デモ動画 | 代表的な操作を選び、開始時の状態、入力、判定や保存、観察できた出力を一組として図と文章で示す。処理の説明に必要なコードを本文に、長い設定例は必要に応じて付録に置く。 | 「この画面の直前に何を操作しましたか。実行後の画面かログは残っていますか。」 |
| 学習曲線・結果表 | 図に先立ち対象データ、分割、比較条件、指標と単位を示す。表示値とその解釈を分け、推定値には推定方法を添える。 | 「この値は学習時と独立したデータで測りましたか。軸と集計単位を教えてください。」 |
| アンケートの棒グラフ・感想 | 評価目的、対象、課題、設問・尺度、有効回答数、集計結果、限界の順に展開する。個別の試用談なら、操作中の観察と本人の発言を区別する。 | 「誰が何を試した後の回答ですか。設問文と有効回答数を確認できますか。」 |
| 進捗・今後・予備スライド | 発表後の完了状況を本人に確認し、実装済み・実験済みは対応する章へ、未実施の案は今後の課題へ置く。予備スライドには手法や条件の説明が残っていることがある。 | 「発表時に予定だったこの比較は、その後実施しましたか。結果を示す資料はありますか。」 |

## 対応を判断するときの例

### 代表操作を一つ追う

「共有」「通知」のような短い語は、対象が見えること、依頼を送ること、状態が変わることなど、異なる操作を指し得る。まず「デモで、誰が何をしたとき、誰の画面にどんな変化が起きましたか」と聞く。二人が関わるなら操作側と相手側の画面各1枚または短い説明で足りる。答えを得てから、入力・送信先・結果の順に節を組み立てる。仕様が不明な間は評価案でも通知の契機などを仮定しない。

主張に関わる場合は、「別の入力経路はあるか」「取り消しや復帰でどの状態に戻るか」「どの条件で拒否されるか」を追加で確認する。課題欄の「修正」「改善」は、まず現状が未実装・一部動作・動作確認済みのどれかを確かめる。重要な質問を一件ずつ答えられる形にし、残りは根拠メモに控える。

### 画面と集計表を読む

画面の追加・編集・一覧が別々に載っているときは、一つのレコードを保存して再表示した証拠があるかを確認する。「完成」とある画面でも、入力、保存、一覧への反映は別々に確かめる。一覧の並び替えと絞り込みのように、実装状況が異なり得る操作は分けて書く。

アンケートでは全参加者数のほかに、設問への回答資格、設問別の有効回答数、尺度の向きを控える。逆転項目がある場合は集計前の変換を確かめる。例として選ばれた設問だけから領域全体の平均や標準偏差を復元しない。発表と提出で題目が変わる場合に備え、表紙には提出者が確認した正式題目を使う。

### 結果の表を本文に移す

主な結果を一つ選び、どの対象・分割で、どの方式をどの設定で動かし、何を集計した値かを一文にする。同じ手法でも実験ごとに負荷や評価集合が異なる。複数の資料に似た図があれば、単位・負荷・試行数・凡例が一致した図同士で比較する。条件が違えば別実験として引用する。

全体平均しか提示されていない場合、対象別の値は推定しない。重要なら、群別の件数・値・重みを質問する。人手評価では誰の回答をどうまとめ、どの条件を満たすと成功かを記す。判定の閾値がある場合は、設定に使ったデータと最終評価に使ったデータを区別する。誤差棒には何を表すか、何回の反復から得たかを添える。

### 収録例で見られた展開

- 段階表示した通信図と画面デモは、ある卒論では全体構成の図と、投稿・詳細表示・チャットの機能別説明に展開された。新しい原稿でも、図の枚数に合わせて節を作るより、ひとつの操作を最後まで説明できる区切りを選ぶ。
- モデル精度の比較と追加評価の予告が並んだ発表では、卒論でも学習結果とデモを記載し、速度・消費電力を含む最終選定を課題に残した。「評価する」と書かれたスライドから得点や順位を補わない。
- あるアンケート発表は、卒論で対象者の経験、試用手順、尺度、集計、自由記述に展開された。一方、ゲームの体験デモは、操作に迷った場面や改善要望の記述につながっていた。後者を定量評価に変換するには新たな根拠が必要になる。

このメモを章立てと質問の判断に使う。過去の数値・対象者・実装条件を新しい研究に当てはめない。特定の先行研究に依拠する主張を書くときは、その文献の該当箇所を直接確認して引用する。
